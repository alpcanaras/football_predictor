**Football Predictor review — 27 September 2026**

The best next investment is trustworthy evaluation and settlement, followed by targeted model and data experiments. The repository has useful foundations, but its present reports do not establish a profitable strategy for either fixed-odds betting or Toto. Both uses are treated as equal priorities in this review.

Scope: inspected the active data, feature, training, prediction, evaluation, blending, pooled model, Toto, ticket, tracking and app paths, plus the notebook value scanner. Ran data diagnostics, targeted reproductions, existing Toto/tracker/ticket checks, and the existing market-feature experiment. Production code and saved models were not changed. This is not a full model retrain or a prospective profitability study.

**What the current evidence says.**

- The processed dataset contains 99,814 matches, 38 leagues, and dates from 2015-01-10 to 2026-09-24. There are no duplicate `(league, Date, HomeTeam, AwayTeam)` keys in this snapshot. Complete 1X2 odds cover approximately 99.96% of rows; that does not establish price freshness or executability.
- Training already uses temporal folds, exponential recency weighting and separate calibration data. The repository already includes pooled cross-league models, Dixon–Coles, market blending, a notebook ROI scanner and a crowd-aware ticket optimizer. These should be improved rather than proposed as new capabilities.
- Existing selected self-tests passed: Poisson-binomial versus Monte Carlo, system optimization on four enumerable instances, parser, tracker roundtrip, and ticket optimization on three enumerable instances. They do not cover the defects below or prove the optimizer is globally optimal on full-size coupons.
- Reran `MPLCONFIGDIR=/tmp/football-audit-mpl OMP_NUM_THREADS=4 ./venv/bin/python scripts/exp_market_feature.py`. It trained on 97,168 matches before 2026-06-01 and evaluated 2,607 later matches:

| Variant | Log-loss, lower is better | Accuracy |
|---|---:|---:|
| Features only | 1.0266 | 47.5% |
| Features plus market | 1.0076 | 50.2% |
| Market features only | 1.0085 | 49.8% |
| Raw normalized bookmaker probabilities | 1.0074 | 50.1% |

The script's paired comparison for features plus market versus book was -0.0003 ± 0.0032, with positive values defined as model improvement. Its best retrospective blend again assigned the model zero weight. These are measurements of this experiment, not a certified leakage-free betting backtest: the feature and odds issues below still apply, the blend weight is selected on the test outcomes, and the confidence calculation assumes independent match losses.

The README's assertion that the question is permanently settled overstates the evidence. One model, feature set and date window failing to beat an aggregate market baseline does not prove that all features are redundant, that every subgroup lacks signal, or that obtainable prices at every bookmaker are efficient. Equally, this run supplies no positive evidence of an actionable edge. Treat the June–September window as an already-inspected research window, not a fresh final test.

**Priority 1: make evaluation reflect what would actually have been known.**

1. **Default validation is empty.** `scripts/config.py:261` sets `TRAIN_CUTOFF = None`; `scripts/validate.py:36` converts that to `NaT`. Verified: `_get_test_data` returns zero rows. This command can finish without evaluating a match. It should fail explicitly when an honest test period cannot be established. Merely choosing the latest 60 days would not fix it if loaded models trained on those rows.

2. **Model history is not enforced.** Per-league model saves lack their training/calibration dates and feature/data versions. `blend.py:194` trusts a requested cutoff and a manually maintained exclusion list. `coupon_backtest.py:43` does not even apply that list. `pooled.py:184` accepts an evaluation cutoff without enforcing the saved model's cutoff; the current pooled metadata says `cutoff: null`, `n_train: 93749`. Notebook last-90-day scoring also cannot establish that saved models excluded that period. Old documented experiments are not necessarily invalid, but rerunning these evaluators after production retraining can silently evaluate on seen outcomes.

3. **The advertised walk-forward validation is one holdout.** `train.py:694` refits before a single trailing window. Replace this with multiple chronological outer windows covering different seasons and league calendars. Within each window: tune features/Elo/hyperparameters on earlier data, calibrate on separate earlier predictions, freeze selection rules, then score the next block. Keep a final untouched or prospective period after research decisions are made.

4. **Elo tuning sees the future validation outcomes.** `run_full_pipeline.py` tunes Elo using all raw data before constructing the 60-day holdout. `elo_tuner.py:121` chooses parameters from correlations over the entire input. This leaks through parameter selection even though individual Elo updates precede each match. Tune inside each outer training window using a downstream forecasting metric. Also unify the two Elo implementations: the tuner regresses to a dynamic mean over its team array; feature generation regresses to the fixed initial mean. Their fitted parameters therefore describe different algorithms.

5. **Same-date results affect other same-date features.** `features.py:595` updates the league home-win rate after each row, and league standings similarly update row by row. Reordering two synthetic matches on the same date changed their pre-match features. Dates alone do not prove one result was available before another prediction. Freeze league-wide state for a prediction batch, or use actual kickoff/result-availability timestamps. Split folds/calibration on date boundaries, not arbitrary rows.

6. **Evaluate the complete deployed probability function.** `validate.py` loads the default XGBoost model alone; live prediction averages engines and may add pooled predictions and market anchoring. Blend and coupon evaluators also differ from this deployed composition. A shared prediction function should accept explicit historical state, odds and model artifacts, with no hidden current-feed lookup during backtests.

Acceptance criteria: nonempty disjoint test windows; artifacts carrying base-fit and calibration cutoffs, data/feature/Elo versions and library versions; assertions on availability dates; frozen out-of-sample predictions saved per match; and a check that changing future results cannot change an earlier prediction.

**Priority 2: remove differences between training features and live features.**

- **Strength of schedule:** `features.py:565` keeps separate home-opponent and away-opponent histories. `utils.py:105` combines all opponents. Choose one definition and use it in both paths.
- **Cards:** historical features include zero-card matches; `utils.py:169` and `:193` omit them. This changes the meaning and inflates live averages.
- **Missing statistics:** training replaces missing shots/corners/fouls/half-time statistics with zero in rolling histories; live snapshot code skips many missing observations. Missing is not an observed zero. Preserve missingness, sample counts and a consistent prior or imputation rule.
- **Season context:** `features.py:345` and `utils.py:34` impose an August boundary on every league. This splits calendar-year leagues mid-season, and can split July-starting European seasons. Prefer source season/competition-stage identifiers. Live standings also need to use the fixture's season, rather than automatically carrying the last historical season forward.
- **Promoted/relegated teams:** historical feature generation runs separately by league, while live team snapshots combine the team's cross-league history. Establish an explicit promotion prior or a shared cross-league strength scale, and reproduce it during historical replay.
- **Elo state:** `Final*Elo` columns are the final ratings of the entire processed league, copied onto historical rows. They are not direct training features, so this is not a claim that the classifier currently trains on final ratings. However, filtering a fully processed CSV and then calling `get_team_stats_table` is unsafe for historical replay. Reconstruct the state from the prefix. Live prediction also needs the same inactivity regression used in historical Elo generation.
- **Actual match date:** Toto's club fallback uses prediction time, rather than the scheduled fixture date, when deriving rest days. Carry match IDs and kickoff dates throughout.

Use one stateful feature implementation for historical replay and upcoming fixtures. Add parity tests for normal weeks, season boundaries, promotion, missing stats and long inactivity. **Priority 3: make Toto payouts and recorded results correspond to the purchased system.**

The existing hit-probability calculation is useful: for a full Cartesian system, a match is covered if its actual outcome appears among the selected symbols, and the Poisson-binomial calculation gives the probability that at least one column reaches a threshold, assuming independent match results.

The payout objective in `ticket.py:116` is a different matter. It multiplies a boolean win indicator by one estimated pot share. It does not count multiple winning columns, distinguish exact prize tiers, subtract ticket costs, or represent tier pots and rollovers. German Toto has separate 10/11/12/13 tiers, and Turkish Spor Toto separates 12/13/14/15; returns depend on winners in the respective tier. See the [official German game information](https://www.westlotto.de/toto/ergebniswette/spielinformationen/toto-ergebniswette-spielinformationen.html) and [Turkish game plan](https://www.sportoto.gov.tr/musterek-oyun-plani.pdf).

A small reproduction illustrates the missing multiplicity: two matches, a double on each, both actual outcomes covered, and a threshold of one correct. Three of the four purchased columns win. The current evaluator counts a single boolean win and pays one share. The code's default `tilt = 0.5` further makes the score a preference-weighted utility, not expected monetary payout. Label that distinction explicitly.

Build a settlement engine that counts exact winning columns in every tier for each simulated outcome. For a Cartesian system this can be computed efficiently: multiply polynomials `(k_i - c_i) + c_i*z`, where `k_i` is selections on match i and `c_i` is 1 if the actual outcome is selected, otherwise 0. The coefficient of `z^r` is the number of columns with exactly r correct. Apply each tier's settlement rules, estimated competing winning columns, own winning columns and costs. Field-size and crowd-dependence assumptions need sensitivity analysis; marginal crowd percentages alone do not identify how actual tickets combine selections. `1/(expected competitors + 1)` is also an approximation to an expected share, especially when expected winners are rare.

The existing optimizer already accepts crowd percentages. Preserve that work, but use genuine entry percentages where available and distinguish official tendencies from observed public selections. Add dated snapshots of crowd shares, sales/field estimates, ticket cost, final tier payouts and rollovers. Optimize expected net return under a stated risk preference, then assess on separate simulations and actual historical coupons. `sweep` already uses a separate simulation seed for evaluation; extend that discipline to the main payout report.

**History currently compares different tickets.** `app.py:828` saves each match's top single pick. At `:870`, `p_played` becomes the system's probability; `:988` saves those singles with the system probability. `track.py:163` grades exact string equality and uses the highest single-outcome probability as expected success. A synthetic `pick='1X'` with a draw was marked incorrect and expected 0.5 instead of its covered probability 0.8. Save the actual masks/columns, scheduled match IDs, stake, submitted ticket choice and forecast version; grade covered matches and all winning columns per tier. Name/date-window lookup can also select the wrong meeting when the same sides play twice close together.

Acceptance criteria: settlement versus enumeration on small systems; realistic multi-tier worked examples; history roundtrip for doubles/triples and contrarian selections; and prospective cost, payout and net-return tracking.

**Priority 4: test bookmaker opportunities at obtainable prices.**

The current market-anchored 1X2 weights give the model weight 0 and the book exponent approximately 1.112. Where these weights apply, the displayed prediction is essentially a sharpened market forecast. Any apparent edge from that transformation is not independent team-model evidence.

Separate the market used to estimate probability from the bookmaker where a bet could be placed. `config.py:310` and `data_loader.py:40` collapse average, single-book, pre-closing and closing 1X2 odds into `OddsH/D/A` without preserving the chosen source alongside them. Raw columns remain in the processed file, so some historical reconstruction is possible. Football-Data explicitly distinguishes pre-closing columns from closing columns marked with C; these snapshots must not be mixed into an earlier decision. [Source documentation](https://football-data.co.uk/notes.txt).

Keep bookmaker, market, line, decimal price, observed timestamp, fixture kickoff and feed source. Archive snapshots rather than overwriting the two fixture CSVs. Reject invalid/incomplete odds tuples and stale quotes; fixture date is not quote freshness. `fixtures.load_cached()` also keeps its in-memory dataframe without an age check. The app's “live” label should reflect the source's actual observation time.

The notebook already calculates unit-stake ROI using `p * odds - 1`, which is the right elementary expected-return expression. Its recent-window evaluation and aggregate odds are insufficient to establish an executable strategy. Extend it into an event-based replay with selection rules fixed on earlier windows, offered prices available at that time, costs/commission where applicable, void handling and an actual bet ledger.

A 50% forecast at odds 1.90 has expected return -5%, even if it is above a de-vigged market estimate of 48%. Disagreement with the market and positive expected return are different measurements. Conversely, a market-quality probability estimate could have value at a sufficiently better obtainable price. Neither argument requires claiming superior prediction for every match.

Candidate experiments, in order:

1. Consensus probability versus a separately recorded available price at the target bookmaker, using simultaneous quotes. Historical cross-book maximums alone do not prove executability.
2. A regularized residual model: start with market log probabilities and learn small corrections, `p = softmax(log(q_market) + delta(features))`. Compare with the unmodified market, calibrated market-only, market-plus-features, and current log-pooling. Freeze model complexity and selection thresholds before outer testing. This is a hypothesis, not an observed improvement.
3. Separate trials for 1X2 and O/U 2.5, with league effects shrunk toward a shared estimate. Do not choose “winning leagues” from the same ROI table used to advertise the strategy.
4. Prospective paper bets. Log every eligible decision, including no-bets, then compare realized net ROI, drawdown, calibration among selected bets and price relative to a reliable de-vigged closing benchmark. Closing-line performance is supporting evidence, not a profit guarantee.

Report uncertainty by resampling matchdays or weeks, preserving related bets on a fixture. Report the number of distinct matches/weeks and all attempted strategies. Additional simulations or overlapping synthetic coupons do not create additional independent historical evidence. A go/no-go decision should depend on effect size and uncertainty over untouched periods, not a universal bet-count threshold.

**Priority 5: improve training efficiency and freshness.**

The current row-based calibration tail withholds up to 700 matches from fitting the base learner. Applying today's split configuration to today's data gives these boundaries; these are not inferred training dates of existing artifacts:

| League | Last base-fit match | Calibration matches | Last available match |
|---|---|---:|---|
| English Premier League | 2025-10-20 | 350 | 2026-09-20 |
| Bundesliga | 2025-10-18 | 281 | 2026-09-20 |
| Turkish Super Lig | 2025-08-30 | 334 | 2026-09-20 |
| MLS | 2025-05-29 | 700 | 2026-09-24 |
| Brazil | 2024-12-05 | 668 | 2026-09-20 |

Thus even a new fit can reserve roughly a year or more of recent outcomes only for calibration. Test calendar-bounded calibration or pooled rolling out-of-sample calibration, while maintaining disjoint fit/calibration outcomes and measuring any distribution shift when base learners are refitted. Calibrate the final deployed ensemble. Do not simply train on calibration labels and reuse the same fitted calibrator without validating that change.

Other specific changes worth testing:

- Start with a small shared hyperparameter search and stronger regularization, then permit per-league deviations only where repeatable outer-window gains justify them. The current default is 200 trials per league/market/engine; most of that compute is better spent on reliable outer tests and feature ablations.
- Compare recent training windows and decay rates inside temporal tuning. Recompute and normalize decay weights separately within each fold: slicing globally normalized weights changes their scale relative to regularization across folds.
- LightGBM tunes `subsample` while leaving `subsample_freq` at its disabled default. Enable bagging deliberately or remove the ineffective dimension. [LightGBM parameter documentation](https://lightgbm.readthedocs.io/en/stable/pythonapi/lightgbm.LGBMClassifier.html).
- XGBoost's `best_iteration` is zero-based; account for that in the final estimator count. The hard minimum of 50 rounds also overrides earlier stopping decisions; validate whether that floor is warranted.
- `_pick_cal_method` selects isotonic by sample count, not demonstrated held-out performance. Test sigmoid/temperature versus isotonic using earlier out-of-sample predictions, particularly with only 500–700 calibration cases. Scikit-learn warns about isotonic overfitting with small calibration datasets. [Calibration documentation](https://scikit-learn.org/stable/modules/generated/sklearn.calibration.CalibratedClassifierCV.html).
- The models named `xGH/xGA` are forecasts fitted to final goal counts, not shot-quality xG measurements. Test Poisson count likelihood, then overdispersion or Dixon–Coles if justified, and evaluate score distributions with log scores as well as point-error metrics. The existing Dixon–Coles code is a usable baseline.
- Enforce coherent market outputs: `P(over 1.5) >= P(over 2.5) >= P(over 3.5)`. Independent classifiers and selective market anchoring do not guarantee this. A common score distribution supplies a useful reference; any reconciliation should be evaluated.
- Stop swallowing calibration/model errors silently in research runs. Store exact feature names, classes, fit/calibration windows, selected parameters, seeds, code/data hashes and environment versions. Checkpoint keys should include the training specification so interrupted runs cannot silently resume under different settings.

**Data additions should earn their cost in matched experiments.**

First prioritize information that makes evaluation and execution possible: timestamped odds, fixture IDs/kickoffs, and dated Toto crowd/payout records. Then test incremental football information in a limited coverage area: lagged non-penalty shot xG for and against; known absences and expected/confirmed lineups at the chosen decision time; manager changes; and all-competition rest, travel and fixture congestion. Current per-league rest counts omit cup and international club matches.

The [StatsBomb open repository](https://github.com/hudl/open-data) contains event and lineup data for selected competitions and is useful for research prototypes. It is not evidence that there is a current production feed covering this project's 38 leagues. Check historical coverage, publication timestamps, availability going forward and permitted use before committing to a supplier. Compare every added feature block against the market-only baseline on the same matches and prediction times; do not infer benefit from feature importance alone.

**Recommended delivery sequence.**

| Stage | Concrete deliverable | Evidence required before advancing |
|---|---|---|
| 1 — Measurement and correctness | Shared causal features, artifact metadata, honest rolling evaluator; actual Toto ticket history | Feature parity and no-future-influence checks; correct system grading; nonempty disjoint outer windows |
| 2 — Price and payout data | Timestamped bookmaker ledger; crowd/payout archive; exact Toto tier settlement | Quote availability checks; settlement versus enumeration and official examples |
| 3 — Focused challengers | Market residual and pooled/no-odds models; alternative calibration; exact payout optimizer | Paired outer-window improvements, selected-bet calibration and independent ticket evaluation |
| 4 — Prospective use | Paper bet and coupon records with frozen selection rules | Repeatable net-return evidence with uncertainty, realistic costs, drawdown and closing-price diagnostics |

My first implementation batch would be stages 1 and the Toto settlement work in stage 2. That would make every later training run and strategy comparison more informative. Model complexity should increase only after the measurements can distinguish a real improvement from leakage, stale state, incorrect payout accounting or selection noise.
